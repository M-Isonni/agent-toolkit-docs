What Agent Toolkit adds

An AI agent can already change an Unreal project without this plugin. Epic's MCP server serves Epic's general toolsets once their plugins are on, Python remote execution runs any editor Python, and the agent can edit the project's files. This chapter shows what changes when Agent Toolkit is installed: measured on real tasks, with examples. It grows with every domain.

How it was measured

  • The agent: Claude Code 2.1.319 with Claude Opus 5.5, running headless on Unreal Engine 5.8.4 (changelist 58902052). Nobody answers its questions.
  • The plugin: Agent Toolkit 0.1.0 at the release candidate, commit e0ecb48.
  • The same tools in every run: Epic's MCP server with all of Epic's toolsets (the All Toolsets plugin on), Python remote execution and the project's files. In every setup the agent's shell is allowed python commands only, so some other commands were refused, and the agent's file tools are refused Agent Toolkit's own folder; a run that reached it anyway is left out (see below).
  • The same prompts in three setups:
    • without: the editor without Agent Toolkit;
    • with: Agent Toolkit installed, nothing else changed;
    • with + instruction: Agent Toolkit plus the instruction from the quick start (step 4).
  • Checked after every run, on the editor and the files, not on what the agent says:
    • Is the task really done?
    • Does Ctrl+Z take the change back?
    • Did the agent claim a success it didn't have?
    • Did the editor survive?
  • Sixteen tasks, two runs per task and setup. Turns, tool calls, tokens, time and cost are medians of the two runs. Tokens count everything the model read and wrote, cached or not. Cost is API-equivalent, that is what the run would cost on the Claude API.
  • Runs that don't measure an ordinary project aren't counted. A run without the plugin that read Agent Toolkit's own files, or a run that called the test project's own helper code, is left out and run again.
  • Runs done again in this pass:
    • One landscape run without the plugin crashed the editor, in the agent's own Python after 111 turns. The task was run again and the table counts the new runs, which favours the setup without the plugin.
    • The comparison's own Ctrl+Z check crashed the editor once, after a Smart Objects run without the plugin, while it undid a Blueprint the agent had made. That task was run again.
    • Both first runs without the plugin in the World Partition corner task read Agent Toolkit's files: the agent searched the plugin's folder for "landscape". They were left out and run again.
  • Two checks were aligned with their prompts after the pass, by the publisher's decision: an answer that ends with "Started: yes" on the last line of its summary, not on a line of its own, answers the package task; and a measurement with the toolkit's stat_snapshot, which writes no file, counts as a profile measurement, as a capture file does. Every run was then checked again from its report and transcript. Five runs changed result, one without the plugin and four with it.
  • The machine: AMD Ryzen 9 5950X (16 cores), NVIDIA GeForce RTX 3090, 64 GB RAM, Windows 10. Times depend on the machine. Cost, tokens and results depend mostly on the model and on the tools' answers, though a slower machine can add a few waiting turns on long jobs such as packaging and cooking.
  • Measured on 2026-11-07 (pass 2026-11-07-e0ecb48).

Its cost was lower on 13 of the 16 tasks, and the medians add up to $4.36 API-equivalent against $20.96 without the plugin: 21 %. It used fewer tokens on 12 tasks.

A task is done when every check of the task passed; Ctrl+Z is counted apart. A false success is a run that said it was done while a check of the task failed.

The sprint input was checked in the running editor, in Config/DefaultInput.ini and in Play. The images were checked on disk, for an exposure that is neither black nor washed out, and the report for the actor that has no mesh. For the navmesh task, "Ctrl+Z works" means an edit you made before asking can still be undone after the build. The bench task's seats were checked in Play, where NPCs look for them.

The hill was checked at its centre and 150 m away, the paint on samples of steep and gentle ground, and the rock share against the 2.34 % the check measures. The trees were counted in the circle, and samples of them were checked for standing on the ground.

Creating an asset is not an undo step in Unreal, so the beep and the animation tasks have no Ctrl+Z column; in the footsteps task, Ctrl+Z must take back the attenuation set on the cue. The comparison renders the beep itself and compares the agent's peak with its own. The retargeted clips were checked against their sources: skeleton, frames, length and motion. The state machines were checked by running each Blueprint on the Mannequin with Speed at 0, 15, 300 and 5, reading its states and the feet.

The World Partition tasks start from a saved level reopened with most of it unloaded. In the corner task one of the landscape's 16 parts, away from the corner, was already loaded, though the prompt says none is. The hill was checked by loading every part of the landscape afterwards and measuring the ground every 12 m, and the houses' layer from the level's files as saved, not from memory.

A build changes nothing in the editor, so the build tasks have no Ctrl+Z column. The cook was checked from the cooker's own list of what it cooked, written during the run; the package from its files under Saved, written during the run, and from the processes left: no packaged game was still running after any run. BuildYrad doesn't exist, and every run said so. A material the user had changed and not saved was still unsaved after every cook run.

Without the plugin, both cook runs stopped before cooking: the shell command that starts Epic's cooker was refused, since the agent's shell is allowed python commands only, and neither agent started the cooker another way. One said that starting it from the editor's Python would get around the refusal. One package run without the plugin started Epic's UAT and then the game from the editor's Python, and saw the game start, but it didn't end its answer with the line the prompt asks for: it isn't counted as done, and since it said it was done it counts as a false success. The other package run had its first shell command refused, concluded that it couldn't run Python either, and stopped, answering "Started: no".

The profiling task was checked on the level and the files: every actor of the Heavy folder visible in game and nothing else changed, Play stopped, a measurement, and the answer's last lines (the median frame time before and after, and whether it got slower). A measurement is a capture file under Saved written during the run, which any setup can make, or a call of one of the toolkit's measuring tools. One run without the plugin timed the frames with its own Python timer and left neither: its answer was right, but it isn't counted as done, and it counts as a false success. With the plugin but without the instruction, one run answered "Slower: no" (see the examples below). The comparison sets Play's window to 1280 x 720 before every run.

What it adds, with examples

Times and costs below are medians, with the quick start's instruction against without the plugin, unless a sentence says otherwise.

The editor stayed up

No run with Agent Toolkit crashed the editor: 64 runs, with and without the instruction. Without the plugin, one landscape run crashed it, in the agent's own Python after 111 turns; that run was done again and isn't in the table.

Ctrl+Z takes the agent's work back

Every Agent Toolkit edit is one undo step; new assets and files written to disk can't be undone, and each answer says whether its change can be. In the sprint task, Ctrl+Z removed the key mappings and the project-wide context in every run with the plugin, with or without the instruction. With the instruction the task also took 37 s instead of 76 s, and $0.27 instead of $0.47 API-equivalent.

Without the plugin, the agent did the same task just as well with Epic's MCP tools, but Ctrl+Z took nothing back: the check found no undo step after either run.

  • Epic's object tool set the key mappings without recording an undo step.
  • Epic's settings tool writes the setting straight to the config file.

Evidence in fewer steps

  • Capture and map check: with the toolkit, the agent finished in 49 s instead of 114 s, at under half the cost. It took 10 turns instead of 23.
  • Play capture: 21 s instead of 65 s, at under a quarter of the cost.

Without the plugin, the agent spent its turns finding a way to make an image and read the map check:

  • in one evidence run, 5 calls failed and one returned an image too large to read before the agent typed a screenshot command into the editor's console box with Epic's Slate inspector; it left your viewport camera at the top-down view;
  • the other evidence run spawned a capture camera from Python and deleted it afterwards;
  • both evidence runs ran the map check as a console command and read its messages from the editor log;
  • both Play runs had a shell command refused and typed a screenshot command into the editor's console box.

With the plugin:

  • evidence.capture_from renders from any camera without touching your viewport, and checks the image before it reports it;
  • evidence.map_check runs the editor's map check on the current level and returns the errors and warnings as data, for example StaticMeshActor_2 Static mesh actor has NULL StaticMesh property;
  • evidence.pie_start, pie_capture and pie_stop each answer once the editor is in the state they report.

Navigation in half a minute

With the quick start's instruction, the agent gave the level a navmesh and answered where an NPC can walk in 31 and 32 seconds, with no failed calls. The answers were right in every run, with and without the plugin: the strip behind the wall and the platform are reachable, the inside of the closed box isn't.

Without the plugin, the time depended on the way the agent found. One run used Python remote execution and finished in 50 seconds, for less than a run with the plugin cost. The other had its first shell command refused and went on with Epic's MCP tools: the editor's navigation test actors never found a path, and the agent ended up typing Python into the editor's console box. Five of its calls failed, and the run took almost seven minutes. Both runs:

  • spawned a navigation bounds volume and sized it by hand;
  • rebuilt the navmesh with a console command;
  • wrote their own path queries in Python.

With the plugin:

  • nav.ensure_bounds covers the level's geometry and adds a volume only when one is needed;
  • nav.build answers once the navmesh is built, without the editor's Build Paths, which clears your undo history;
  • nav.path_test says whether a place is reachable and, when it isn't, why: in the box, the end is on another island;
  • nav.coverage measures the walkable area and draws the islands on a picture.

Smart Objects in under half the time, and undoable

Without the plugin, the agent made a correct bench in both runs, but it took almost three minutes and about 35 calls, 6 and 9 of them failing, and Ctrl+Z couldn't remove the Smart Object component afterwards. Python can't set a seat's offset, rotation or ID directly; one agent set them through text import. With the instruction it took 73 seconds, at under half the cost, and Ctrl+Z removed the component in both runs.

With the plugin:

  • smart_objects.create_definition makes the definition from a list of seats and checks that it loads and passes validation;
  • smart_objects.attach adds the component to the actor as one undo step and checks that the seats can be found;
  • smart_objects.query lists the Smart Objects and free seats around a point.

Terrain in under a minute, instead of ten

With the plugin, the agent raised the hill, painted grass and rock and reported the rock's share (2.4 %, measured 2.34 %) in every run; with the instruction it took 33 and 39 seconds and 9 turns. Ctrl+Z took everything back.

Without it, the agent finished too, in both runs, but it took 8 and 13 minutes, 113 and 92 turns, and $3.60 and $4.23 API-equivalent. It drew the hill and the paint into render targets with materials it wrote, and imported them with Epic's Python. Python can't add a paint layer to a landscape, so in both runs the agent created the layers by driving Landscape mode's panel with Epic's UI tools. Ctrl+Z took those runs back too. A third run, which isn't counted, crashed the editor.

With the plugin:

  • landscape.sculpt_region raises the terrain by an exact amount, with a falloff, as one undo step, and reads the heights back;
  • landscape.paint_layer creates the layer when the landscape lacks it and paints by slope, height or mask, the other layers giving way, with the coverage measured on the result;
  • every edit goes into the toolkit's own edit layer, so your layers stay as they were.

A forest that Ctrl+Z removes

Both setups planted 785 trees and counted them right. With the plugin it took 34 seconds instead of 64, and $0.17 instead of $0.24 API-equivalent, and Ctrl+Z removed the trees in every run. Without it, the agent added the instances from Python with a line trace for each tree; that path records no undo step, so after the task the trees could only be deleted by hand.

Sounds checked, though the agent can't listen

With the plugin, the agent built the beep and reported its peak from the toolkit's offline render: 0.0 dBFS, a 1.01 s tone that stops by itself, in every run, in 18 to 29 seconds. With the instruction, building it took one call.

Without it, the agent built a correct beep through Epic's MetaSound builder in both runs, but couldn't measure it. Both recorded the editor's output while the beep played, and both recordings peaked at -9.0 dBFS, 9 dB below the sound itself. Both agents then answered 0 dBFS from the sine's full-scale setting, which was right; one said it hadn't measured the signal itself. The runs took about a minute and a half, at about two and a half times the cost.

With the plugin:

  • metasound.build_from_spec checks the whole spec before anything is created, renders the new MetaSound offline with its own generator, and answers its peak, RMS, start, length and clipping;
  • audio.render_check does the same for any sound, with a waveform picture for the agent;
  • a WAV of what was measured is saved for you to listen to.

Footsteps in 23 seconds instead of five minutes, and Ctrl+Z works

Both setups made the cue and the attenuation right in every run. Without the plugin, both agents found that Python couldn't build the cue's graph in the Sound Cue editor. One let Epic's Sound Cue factory make the random node and the three wave players, then added the modulator by dragging it in the Sound Cue editor with Epic's UI tools: two and a half minutes. The other built the tree in Python first, found that the editor showed an empty graph, and rebuilt it through the Sound Cue editor: about 50 calls of Epic's UI tools, 102 turns and 8 minutes. Ctrl+Z took the attenuation back in one of the two runs.

With the plugin it took 23 seconds at about a tenth of the cost, and Ctrl+Z took the attenuation back in every run:

  • soundcue.create builds the whole tree in one call, checks it node by node and renders it;
  • audio.create makes the attenuation and reports its gain at the source, halfway and at the end of its falloff;
  • audio.assign sets it on the cue as one undo step and says when another setting would override it.

Retargeting in under a minute

Both setups retargeted the three clips right in every run: the frame counts and lengths of the sources, and an idle, a walk and a run that move as the Mannequin's do, scaled to the taller character. Without the plugin, the agent built the IK rigs, the retargeter and the batch through Epic's Python in about 80 seconds, and checked the result by its numbers only: neither run made a picture.

With the plugin it took 46 seconds, at about three quarters of the cost:

  • retarget.create makes the retargeter, and an IK rig for each character from the engine's skeleton template, maps the chains and shows both characters side by side in a picture;
  • retarget.batch checks every new clip against its source: skeleton, frames, length, rate and motion;
  • animation.pose_thumbnail shows a pose of a new clip on its character.

A state machine in under a minute, instead of fifteen minutes of mouse input

With the plugin, the agent built the Animation Blueprint from one spec, and the same call ran it outside Play with a Speed timeline: Idle, Move, Idle, in under a minute in every run. In three of four runs, the first spec used a key the tool doesn't take; the tool refused it before making anything and named the keys it takes.

Without it, the agent can't add states or transitions to a state machine: neither Epic's Python nor its MCP tools can. Both runs drove the editor's interface instead. One built the states but couldn't draw the transitions with Epic's Slate inspector, and stopped after 196 turns and 14 minutes, saying the Blueprint wasn't finished. The other drew the transitions with mouse input sent from a Python script; its Blueprint was right, after 189 turns, 16 minutes and about 25 times the cost.

With the plugin:

  • animbp.create_from_spec checks the whole spec (variables, clips, blend spaces, rules) before anything is made, then builds and compiles the Blueprint; given a timeline of variable values, it also runs it as animbp.simulate does;
  • animbp.simulate runs it offscreen on a timeline of variable values and reports each state change, with pictures, and leaves nothing changed;
  • animbp.verify_in_pie checks the same in Play.

An unloaded corner of the world in half a minute instead of four and a half minutes

On a World Partition level, the part of the landscape the agent must change usually isn't loaded. Both setups raised the hill right in every run, as one undo step, and changed nothing else. Without the plugin, the agent loaded the corner's landscape part, drew the heights into a render target with a temporary material and wrote them with the engine's heightmap import inside one transaction: almost four and five and a half minutes, 28 and 42 turns.

With the plugin it took 26 and 35 seconds, at about a fifth of the cost: landscape.sculpt_region loads the area it needs by itself, keeps your undo history, makes the change one undo step, and reads the heights back. In this task it loaded four landscape parts and gave them its own edit layer, so a later save would write them too, though only the corner's heights changed; every agent with the plugin said so. Every other World Partition change works the same way: foliage, navigation, data layers and Smart Objects load what they need, and world_partition.save writes the files with unsaved changes, and only those, with no dialog.

A build that says what it really did

Epic's cooker skips a level it can't find with only a warning, and a package can end with exit code 0 without every file a game needs. With the plugin, settings_check refused the misspelled level by name before anything started, in every cook run, and the pre-checks named the unsaved material: every agent then cooked without it, with ignore_unsaved, instead of saving your work. Each answer was checked against what the build left: the cooker's own list for the cook, and for the package every file a Win64 game must hold, written by this build, then the game started once, headless, until it reached its first level, with nothing left running.

The build runs as a job, so the editor stays usable meanwhile and only saving waits. In every package run with the plugin, the build took about a minute and the game reached its first level in the launch check.

A slowdown measured, with the conditions said

Without the plugin, both agents found the slowdown: the median frame time rose from about 10 ms to 19 ms, 88 %. One had its first shell command refused and went on with Epic's MCP tools alone: it started csvprofile frames=600 by typing it into the editor's console box with Epic's Slate inspector, then read the frame times back from the CSV file: 46 turns and $1.40 API-equivalent. The other timed the frames with its own Python timer, after turning off the frame-rate cap and vsync, and kept no capture.

With the plugin, csv_capture records Play with Unreal's CSV profiler in one call, leaving out the warm-up frames, and stat_snapshot samples the same numbers without writing a file. Both answer with the median, the thread that bounds the frame, the GPU time and the conditions they measured under, and csv_capture adds a chart. Every agent with the plugin said what its numbers were taken under, and that in Play the editor's own work set the frame time: the game thread took 13 to 15 ms. The GPU's extra time (from about 3.3 to 6.5 ms) barely showed: the median rose by 0.37 to 2.26 ms. Three of the four runs said it got slower. The fourth, without the instruction, found two measurements of the same state 0.36 ms apart and answered "Slower: no" for a rise of 0.37 ms; the check counts that answer as wrong. Several agents pointed to a standalone game for a clearer number, and game_capture measures one as a job.

The two setups didn't measure the same frame. The runs without the plugin started Play in the editor's large level viewport, while the agents with the plugin played in the project's 1280 x 720 Play window; with more pixels, the GPU did more work (5.0 ms before, 16.8 ms after, in the run that kept a CSV capture). A separate check on the same scene found the same frame with Unreal's own CSV profiler, stat_snapshot and csv_capture, and with or without Agent Toolkit installed: the plugin adds no cost to Play. In that check and in every run with the plugin, the editor reported the render thread as 0 ms, Unreal's own profiler included.

With the instruction, a run took about two minutes and $0.46 API-equivalent, against nearly three minutes and $1.40 without the plugin.

Safer settings

To make the sprint context active for every player, the agent without the plugin used Epic's settings tool. That tool replaces the whole list of default contexts, and the change goes straight to Config/DefaultInput.ini. In a project that already has default contexts, the list it writes is the only one left.

Agent Toolkit's input.add_to_player adds to the list or updates it, and can be undone. Nothing reaches the file until evidence.save_assets writes it after the source-control check.

Mistakes caught before they cost you

Agent Toolkit tools check what they are given and say how to fix it. In this pass they refused, before anything changed, a level that doesn't exist (every cook run with the plugin), a gameplay tag the project doesn't define (every bench run with the plugin) and an Animation Blueprint spec with a key they don't take (three state machine runs of four), and each answer said what to change. Other checks:

  • A misspelled key such as LeftShfit is refused, with the right name suggested. In Python, a misspelled key makes a mapping that never fires.
  • A mapping context stored in a plugin can't be a default context, because Enhanced Input applies default contexts from game content only. The tool refuses it instead of failing silently.
  • A change while Play is running is refused, so the agent doesn't edit the level the game is using.

What it doesn't change

  • Navigation answers are the same. Without the plugin the agent built a correct navmesh and answered right in both runs, and your undo history survived: the console command it used doesn't clear it. One of those runs took 50 seconds and cost less than a run with the plugin. What Agent Toolkit adds there is a steady time with the instruction (31 and 32 seconds, against 50 seconds and almost seven minutes without it), the coverage picture and the island check.
  • Your agent has to use it. Without the quick start's instruction, one navmesh run and one data layer run of two used Python only; that data layer couldn't be undone. Add the instruction from step 4 of the quick start.
  • Foliage counts are the same. Without the plugin the agent planted and counted the forest right in both runs. What Agent Toolkit adds there is undo, speed and a picture of the result.
  • Retargeting works without the plugin. Epic's Python makes IK rigs, retargeters and batches, and the agent without the plugin retargeted the clips right in both runs. What Agent Toolkit adds there is speed, the side-by-side picture and the check of every clip.
  • Data layers work without the plugin. Epic's Python has a data layer API, and the agent without the plugin made the layer, filled it and saved it right in both runs, cheaper than with the plugin: $0.18 against $0.27 API-equivalent with the instruction. What Agent Toolkit adds there is undo: Ctrl+Z took the change back in both runs with the instruction, and in neither run without the plugin.
  • Packaging can work without the plugin. Epic's UAT runs from the editor's Python: one run without the plugin packaged the project and started the game that way, for $0.24 API-equivalent; the other stopped when its first shell command was refused. A run with the plugin and the instruction cost about $0.49: many of its calls asked the build job for its state while it ran (22 of 31 in one run, 12 of 27 in the other). What Agent Toolkit adds there is the job, the check of every file the package needs and a launch check that leaves nothing running.
  • The sample is small: sixteen tasks, two runs each, one model, Unreal Engine 5.8.4 and one machine. Every new domain adds its own tasks to this chapter.

Measuring keeps the toolkit honest

Measuring also caught a bug in Agent Toolkit itself: its images were darker than the viewport. Unreal's scene capture writes linear colour, and the toolkit saved it without converting it to sRGB.

After the fix, an evidence image of the test level is within 0.04 of the viewport's own screenshot, and an automated test keeps it there. The results above were measured with the fix.

Earlier landscape and foliage runs caught three more:

  • Half-buried trees. The engine's cone has its pivot at its centre. Painted foliage sits on its pivot, so every agent, with or without the plugin, found the trees half under the ground and raised them by hand, and with the instruction that took 36 to 68 turns. foliage.paint now raises each instance by the mesh's pivot height above its base times its scale; in this pass the task took 9 turns in both runs with the instruction.
  • Clearing an empty area claimed a change it hadn't made, and the toolkit's own undo check failed it. It now answers that there is nothing to remove.
  • Roads with a bend had a sharp kink at the middle point, seen in the tutorial's picture: the toolkit turned the spline's points in a different order from the editor's own spline tool. It now follows the editor's order.
